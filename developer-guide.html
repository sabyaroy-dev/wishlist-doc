1. Project Overview

Lonigma Wishlist is a production Shopify app with these major surfaces:

Surface Location Runtime Auth model
Embedded admin app src/app/routes/app.* React Router v7, Polaris Shopify admin session
Storefront app proxy APIs src/app/routes/frontend.api.* React Router server routes Shopify app-proxy HMAC / public storefront context
Shared wishlist page src/app/routes/frontend.shared.$id.tsx React Router route Public signed/share token flow
Webhooks src/app/routes/webhooks.* React Router action routes Shopify webhook HMAC
Storefront UI source src/extensions/wishlist-storefront/ Lit 3, Vite Browser storefront
Theme App Extension src/extensions/wishlist/ Liquid, generated JS/CSS assets Shopify theme runtime
Database src/prisma/schema.prisma Prisma + PostgreSQL Shop-isolated rows
Background workers src/scripts/run-*.ts Node + tsx Server environment

The app supports wishlist creation, guest and customer identity, PDP/PLP hearts, drawer/modal/page wishlist shells, shared wishlists, save-for-later, cart wishlist actions, analytics, exports, Klaviyo integration, notifications, plan gates, and Shopify App Pricing sync.

3. Prerequisites

Supported developer environments:

  • macOS
  • Linux
  • Windows 11 with WSL2 Ubuntu

Required tools:

  • Docker with Compose v2
  • Node >=20.10
  • Yarn classic 1.22.22 through Corepack
  • GNU/BSD make
  • Shopify CLI
  • Google Chrome for browser E2E
  • Access to a Shopify Partner organization and development store

Recommended Node/Yarn setup:

corepack enable
corepack prepare yarn@1.22.22 --activate

Use python3 for scripts and shell commands in this repository. Do not use the python command name.

Windows + WSL2 rules:

  • keep the repo under the Linux filesystem, for example ~/shopify-wishlist
  • do not work from /mnt/c
  • run Node, Yarn, Make, Shopify CLI, and Docker commands inside Ubuntu
  • use Windows Chrome only for browser-driving flows that need a signed-in browser

4. First-Time Setup

Clone the repository:

git clone git@github.com:lonigma/shopify-wishlist.git shopify-wishlist
cd shopify-wishlist

Create the root .env from example.env if present and set the Docker Compose values:

COMPOSE_PROJECT_NAME=shopify-wishlist
HOST_PORT_POSTGRES=50001
HOST_PORT_MAILPIT_SMTP=1025
HOST_PORT_MAILPIT_WEB=8025
HOST_PORT_MINIO=9000
HOST_PORT_MINIO_CONSOLE=9001

Start local infrastructure:

make env-up

Install app dependencies:

cd src
yarn install

Create the app .env:

cd src
cp example.env .env

Populate Shopify app variables:

cd src
shopify app env show

At minimum, ensure src/.env has the Shopify API key, secret, scopes, app URL, and database URL required by the selected Shopify app config.

Example local src/.env shape:

SHOPIFY_API_KEY=replace-with-app-api-key
SHOPIFY_API_SECRET=replace-with-app-secret
SCOPES=read_products,write_products,read_customers,write_customers
SHOPIFY_APP_URL=https://your-current-tunnel.trycloudflare.com
SHOPIFY_DATABASE_URL=postgresql://wishlist:admin@localhost:50001/wishlist

SESSION_SECRET=replace-with-local-random-secret
SHOPIFY_APP_HANDLE=wishlist-stg

SMTP_HOST=127.0.0.1
SMTP_PORT=1025
S3_ENDPOINT=http://127.0.0.1:9000
S3_ACCESS_KEY_ID=minioadmin
S3_SECRET_ACCESS_KEY=minioadmin
S3_BUCKET=wishlist-exports-dev

Keep real secrets in ignored local files or the deployment platform's secret store. Do not commit .env.

Run Prisma setup:

make migrate

Optional local MinIO bucket setup for exports:

make minio-bucket-init

7. Local Development Tunnel

The default yarn dev flow uses Shopify CLI's Cloudflare quick tunnel. The tunnel URL changes after restarts, and Shopify may cache the previous embedded app URL in an already-open admin tab.

Daily workaround with quick tunnels:

  1. Start cd src && yarn dev.
  2. Let Shopify CLI update the app URLs.
  3. If the embedded admin iframe is blank after a restart, close the stale admin tab.
  4. Reopen the app from the Partners Dashboard or the merchant apps list.

Planned named tunnel flow:

cd src
yarn dev --tunnel-url=https://<your-handle>-wishlist.dev.<lonigma-domain>:3000

Run Cloudflare Tunnel separately:

cloudflared tunnel run <your-handle>-wishlist-dev

The :3000 suffix in Shopify CLI's --tunnel-url is the local port the CLI binds to, not the public HTTPS port.

8. Database And Prisma

The Prisma schema is src/prisma/schema.prisma. The app uses PostgreSQL through SHOPIFY_DATABASE_URL.

Safe migration apply:

make migrate

Granular commands:

make prisma-generate
make prisma-migrate-deploy

Create a development migration after editing schema.prisma:

make prisma-migrate-dev name="add_some_table"

Direct commands from src/:

yarn prisma generate
yarn prisma migrate deploy

Database rules:

  • keep data shop-isolated by shop
  • make schema changes backward-safe unless an approved pre-production spec explicitly says no migration path is required
  • do not delete or rewrite migrations without explicit approval
  • preserve idempotency for webhook and worker retry paths

Example shop-scoped Prisma service pattern:

import db from "../db.server";

export async function getWishlistForShop(input: {
  shop: string;
  wishlistId: string;
}) {
  return db.wishlist.findFirst({
    where: {
      id: input.wishlistId,
      shop: input.shop,
    },
    include: {
      items: {
        orderBy: { createdAt: "desc" },
      },
    },
  });
}

Example idempotent create pattern:

import db from "../db.server";

export async function reserveSavedItemUsage(input: {
  shop: string;
  operationId: string;
  quotaWindowKey: string;
  source: string;
}) {
  return db.savedItemUsageLedger.upsert({
    where: {
      saved_item_usage_ledger_shop_operation_unique: {
        shop: input.shop,
        operationId: input.operationId,
      },
    },
    update: {},
    create: {
      shop: input.shop,
      operationId: input.operationId,
      quotaWindowKey: input.quotaWindowKey,
      source: input.source,
    },
  });
}

Use the actual compound unique field name generated by Prisma for the model you touch. Check node_modules/.prisma/client/index.d.ts or existing services before copying an upsert shape.

Example admin route loader/action pattern:

import { json, type ActionFunctionArgs, type LoaderFunctionArgs } from "@remix-run/node";
import { Form, useLoaderData } from "@remix-run/react";
import { authenticate } from "../shopify.server";
import { getSettings, saveSettings } from "../services/settings.server";

export async function loader({ request }: LoaderFunctionArgs) {
  const { session } = await authenticate.admin(request);
  const settings = await getSettings(session.shop);

  return json({ settings });
}

export async function action({ request }: ActionFunctionArgs) {
  const { session } = await authenticate.admin(request);
  const formData = await request.formData();
  const wishlistNoun = String(formData.get("wishlistNoun") ?? "").trim();

  if (!wishlistNoun || wishlistNoun.length > 40) {
    return json({ error: "Invalid wishlist label." }, { status: 422 });
  }

  await saveSettings(session.shop, { wishlistNoun });
  return json({ ok: true });
}

export default function StorefrontSettingsRoute() {
  const { settings } = useLoaderData<typeof loader>();

  return (
    <Form method="post">
      <input name="wishlistNoun" defaultValue={settings.wishlistNoun} />
      <button type="submit">Save</button>
    </Form>
  );
}

Prefer the project's existing Polaris components and route helpers over this minimal HTML when editing real admin screens. The important pattern is admin authentication, shop-scoped service calls, and server-side validation.

Example app-proxy route shape:

import { json, type ActionFunctionArgs } from "@remix-run/node";
import { requireStorefrontRequestIdentity } from "../utils/request-identity.server";
import { addItemToWishlist } from "../services/storefront-wishlist.server";

export async function action({ request }: ActionFunctionArgs) {
  const identity = await requireStorefrontRequestIdentity(request);
  const body = await request.json();

  const productId = String(body.productId ?? "");
  const variantId = body.variantId ? String(body.variantId) : null;

  if (!productId.startsWith("gid://shopify/Product/")) {
    return json({ error: "Invalid product." }, { status: 422 });
  }

  const result = await addItemToWishlist({
    shop: identity.shop,
    customerId: identity.customerId,
    guestId: identity.guestId,
    productId,
    variantId,
  });

  return json({ item: result });
}

Match the real helper names in the current route before implementing. This snippet shows the expected boundary: authenticate the storefront request, validate JSON, then call a shop-scoped service.

The extension directory itself ships only Shopify-approved Theme App Extension directories:

  assets/      generated JS/CSS chunks written by Vite
  blocks/      Liquid app blocks and app embed
  locales/     en.default.json plus translations
  snippets/    Liquid-only shared fragments

Do not add TypeScript, tests, Vite inputs, or build-only files inside src/extensions/wishlist/. Those belong in src/extensions/wishlist-storefront/.

Storefront development rules:

  • use Light DOM for Lit components so merchant theme tokens cascade
  • keep styles in src/extensions/wishlist-storefront/src/styles/wishlist.css
  • use CSS custom properties from the appearance token system
  • do not reintroduce the old Alpine implementation or Shadow DOM approach
  • do not treat archived design handoff folders as binding source of truth
  • read current code before changing PDP/PLP heart, drawer, modal, page, cart save-for-later, shared page, alerts, or admin storefront tabs
  • add or update component tests for meaningful UI behavior
  • run browser verification for storefront changes before release claims

Theme App Extension development rules:

  • do not hand-edit generated files in src/extensions/wishlist/assets/
  • edit storefront JS/CSS in src/extensions/wishlist-storefront/, then run yarn build
  • edit Liquid block placement, schema, locale wiring, and metafield reads in src/extensions/wishlist/blocks/
  • every runtime-rendered string must be passed to the Lit component through attributes or data-l10n
  • add new translation keys to en.default.json and mirror them into every locale file
  • set data-lonigma-wl on root elements that need token styling
  • use | json for strings embedded into JSON attributes or script islands
  • use | escape for plain HTML attributes
  • never pipe merchant text through | t
  • keep app embed behavior storefront-wide and lightweight

12. Appearance Tokens And Metafields

The app embed lonigma_wl_appearance.liquid emits a low-specificity token stylesheet from merchant-owned metafields in namespace:

lonigma_wishlist

The app uses merchant-owned metafields because Liquid needs theme-side reads. App-reserved namespaces such as $app:* are not readable by merchant themes.

Appearance writes flow through applyAppearanceUpdate in:

src/app/services/appearance-tokens.server.ts

The saga:

  1. validates inputs, contrast, custom CSS, and SVG icons
  2. persists the Setting row in Postgres
  3. mirrors storefront-readable values to Shopify metafields
  4. compensates successful metafield writes if a later write fails
  5. rolls back the local Setting row if the external write fails

Do not report admin save success while Postgres and Shopify metafields disagree.

Example token read in Liquid:

{% assign wishlist_noun = shop.metafields.lonigma_wishlist.wishlist_noun.value | default: 'Wishlist' %}

<style data-lonigma-wl-tokens>
  :where(lonigma-wl, [data-lonigma-wl]) {
    --wl-noun: {{ wishlist_noun | json }};
    --wl-color-accent: {{ shop.metafields.lonigma_wishlist.accent_color.value | default: '#111827' | json }};
  }
</style>

Example server-side update call shape:

await applyAppearanceUpdate({
  shop,
  admin,
  input: {
    accentColor: "#111827",
    buttonTextColor: "#ffffff",
    wishlistNoun: "Wishlist",
    customCssRaw: ".wl-heart { min-width: 44px; }",
  },
});

Validate contrast, SVG, and custom CSS before writing metafields. Do not bypass the saga for convenience updates.

Example minimal fetch helper for local debugging only:

type PartnerGraphqlResponse<T> = {
  data?: T;
  errors?: Array<{ message: string }>;
};

export async function partnerGraphql<T>(
  query: string,
  variables: Record<string, unknown>,
): Promise<PartnerGraphqlResponse<T>> {
  const orgId = process.env.SHOPIFY_PARTNER_ORG_ID;
  const version = process.env.SHOPIFY_APP_PRICING_API_VERSION ?? "2026-07";
  const token = process.env.SHOPIFY_PARTNER_API_ACCESS_TOKEN;

  if (!orgId || !token) {
    throw new Error("Missing Partner API configuration");
  }

  const response = await fetch(
    `https://partners.shopify.com/${orgId}/api/${version}/graphql.json`,
    {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "X-Shopify-Access-Token": token,
      },
      body: JSON.stringify({ query, variables }),
    },
  );

  return response.json() as Promise<PartnerGraphqlResponse<T>>;
}

Do not log variables, headers, or raw responses from Partner API calls in committed code. Use the readiness script for normal checks because it handles redaction.

Security rules:

  • keep ~/.shopify at mode 700
  • keep ~/.shopify/config.env at mode 600
  • grant Manage apps only unless a later approved task requires more
  • rotate tokens after exposure or offboarding

type InternalPlan = "free" | "starter" | "growth" | "scale";

const SHOPIFY_APP_PRICING_PLAN_HANDLES: Record<InternalPlan, string[]> = {
  free: ["free", "test-free"],
  starter: ["starter", "test-starter"],
  growth: ["growth", "test-growth"],
  scale: ["scale", "test-scale"],
};

export function mapShopifyHandleToInternalPlan(handle: string): InternalPlan | null {
  for (const [plan, handles] of Object.entries(SHOPIFY_APP_PRICING_PLAN_HANDLES)) {
    if (handles.includes(handle)) {
      return plan as InternalPlan;
    }
  }

  return null;
}
